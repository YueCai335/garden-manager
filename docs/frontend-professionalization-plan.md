## 0. 给执行 agent 的说明

本方案面向实际实现。按任务顺序交付可验证的小改动，每个任务包含文件范围、行为、验收和测试。先读 `AGENTS.md`、`docs/project-strategy.md`、`docs/decisions/README.md` 和 ADR-0061，再读具体任务对应的实现与测试。

### 0.1 已确认的用户要求

1. 产品采用三个层级：全局工作区、具体花园、具体种植区。
2. **AI Garden Note 是全局一级功能和首页高频入口。用户打开首页就能开始写笔记，无需先选择某一个花园。**
3. 用户会在同一天操作前院、后院等多个花园。产品目标包括一段笔记对应多个花园的多条已完成操作。
4. 反馈统一为表单局部反馈和全局保存／同步反馈。
5. 未保存的表单草稿受到保护，其他操作不会静默重置它。
6. 本次专业化覆盖视觉层级、编辑器响应式、删除和无障碍交互、产品文案、CSS 与组件职责。

### 0.2 本方案的技术细节与授权范围

导航位置、具体 URL、色值、断点和批量 AI 接口是本方案给出的推荐默认实现。它们是供用户整体审阅的设计，不冒充此前已经逐项确认的决定。用户明确要求按本方案实施后，执行 agent 将涉及材料性决定的细节记入 ADR，连续完成已授权的本地工作；无需对每个按钮或文件拆分重复询问。

跨花园多事件 AI 是独立的完整功能任务，包含在本方案中，不得用首页加一个入口冒充已实现。其接口与 AI 输出契约扩展列在任务 T08。用户仅授权前端改版时，先交付 T00—T07，明确标注 T08 尚未执行；用户授权整份方案时，包含 T08 的本地实现与离线验证。

## 1. 改版后的产品结构

### 1.1 一级导航与页面归属

采用紧凑顶部导航，避免长期占用花园编辑器的横向空间。

桌面一级导航顺序：`Overview`、`AI Garden Note`、`Care`、`Plant Guide`、`Plant Doctor`。所有页面右上角显示保存／连接状态。首页的 AI 输入区始终是直接入口，导航链接只是其他页面回到笔记工作区的补充。

进入具体花园后，在页面标题附近显示花园名称及切换器；二级导航为 `Garden Plan`、`Care`、`Next Season`。切换花园保留当前模块，目标种植区参数随之清除。花园名称来自 URL 对应实体，不由上一次 `selectedGardenId` 暗中决定。

| 页面／能力 | 归属 | 关键行为 |
| --- | --- | --- |
| Overview | 全局 | AI 快速输入、待办摘要、花园缩略图 |
| AI Garden Note | 全局 | 默认跨花园工作区，原文先输入，具体目标在草稿中核对 |
| Care 全局视图 | 全局 | 聚合所有来源的记录／任务，清楚标注所属范围 |
| Plant Guide | 全局 | 花园上下文可选，未选时不自动绑定某花园 |
| Plant Doctor | 全局入口、记录归属具体花园 | 保留已有诊断／照片限制，明确选择目标花园 |
| Garden Plan | 花园 | 布局总览、花园属性和种植区入口 |
| Care 花园视图 | 花园 | 该花园记录，注明适用的全局记录 |
| Next Season | 花园 | 该花园下一年计划与轮作指导 |
| Next Season 总览 | 全局辅助入口 | 保留现有跨花园规划访问能力；不提升为首页大色块 |
| Planting area inspector | 种植区 | 物理属性、植物布局、植物编辑 |

### 1.2 推荐路由表

| URL | 页面 | 参数规则 |
| --- | --- | --- |
| `/` | Overview | 工作区恢复后渲染首页 |
| `/gardens/new` | 新建花园 | 创建完成进入对应 Garden Plan |
| `/gardens/[gardenId]/plan` | 花园编辑器 | `?area=[areaId]` 打开指定种植区 |
| `/gardens/[gardenId]/care` | 花园养护 | `?view=tasks` 或 `history`，默认 tasks |
| `/gardens/[gardenId]/season` | 花园下一季计划 | 保留当前下一年规则，不新增任意年份功能 |
| `/care` | 全局养护 | `?view=tasks` 或 `history`；默认汇总全部来源 |
| `/notes` | AI Garden Note | 原文和生成结果不写入 URL |
| `/guide` | Plant Guide | 可选 `?garden=[gardenId]` |
| `/doctor` | Plant Doctor | 可选 `?garden=[gardenId]`；保存时必须明确归属 |
| `/season` | 跨花园下一季总览 | 保留现有整体浏览能力与花园筛选 |

实体 ID 做 URL 编码。workspace ID、原文、照片路径和业务记录内容不放入地址栏。深链只在当前已恢复的工作区内查找花园；此项目尚无账户共享能力，URL 不代表他人能访问同一份数据。

无效 garden ID：显示“Garden not found in this workspace”和返回首页入口，不退回任意选中的花园。有效 garden、无效 area ID：保留花园页面，显示种植区不存在的提示，提供关闭提示并清除 area 参数的入口。`view` 无效时归一为 tasks。

### 1.3 桌面与手机导航

- 桌面：顶部品牌、5 个一级链接、同步状态；当前链接用文字、底线或背景共同标记。
- 手机：第一行品牌＋菜单按钮＋简短同步状态；展开菜单显示同样的 5 个文字链接。使用普通可展开导航，不添加 `role=menu`。
- 菜单按钮具备 `aria-expanded` 和 `aria-controls`。选择链接后关闭菜单；关闭时焦点回到按钮。
- 花园二级导航在小屏可以独立横向滚动，不能引发整个页面横向滚动。
- 路由导航用 `Link`，表单提交与原地操作用 `button`。普通导航不模拟 ARIA tabs。
- 同一地址同一状态重复点击不反复堆叠历史。打开种植区使用一次 push，编辑字段不写历史。
- 页面主标题采用一个 `h1`；内容分组使用 `h2/h3`。增加“Skip to content”。

## 2. 首页的具体布局

首页从上到下采用以下顺序，直接落实“打开就经常使用 AI 笔记”的要求。

### 2.1 页面头

- 标题：`Your garden workspace`。
- 简短副文案：`Record today's work and keep track of every garden.`
- `Add garden` 为次级操作，放在花园分组标题旁，而非抢占 AI 录入主操作。
- 不添加无数据支持的天气、积分、增长趋势、效率分数或“AI insights”。

### 2.2 首屏 AI Garden Note 输入区

在页面头后立即显示一块完整宽度的输入区，桌面建议最大文字宽度 880px；页面可留旁侧空间给简短待办摘要。手机上输入区先于摘要。

必需元素：

1. 标题 `AI Garden Note`。
2. 标签 `What did you do in your gardens?`。
3. 可直接输入的 textarea，初始 3 行，最小高度 112px。
4. 字数计数，沿用 500 Unicode code points，不能改成 JavaScript UTF-16 length。
5. `Review draft` 主按钮；生成前含义是进入审核，不暗示已经写入记录。
6. `Add manually` 次级入口。
7. 模式提示：实时辅助、演示示例、连接不可用分别显示真实状态。

首页输入与 `/notes` 使用同一个草稿来源。点击 `Review draft` 后转入 `/notes`，原文保留，明确的一次点击最多触发一次请求；路由挂载、刷新、React Strict Mode 均不能自动重新调用模型。可将“本次显式提交”的处理放在持久 provider 的 action 中，而非页面 useEffect。

T08 完成前，帮助文案说明“一次起草一条浇水或施肥记录”，允许同一会话切换花园继续添加记录。T08 完成并验证后才把提示替换为多事件示例：“今天给前院番茄浇了水，又给后院高床施了肥。”

公开演示的批量模式未开放时，同一首页入口展示限制并允许查看示例或手动录入。不能用批量示例吸引用户提交后，再无说明地拒绝。

### 2.3 今日待办摘要

- 只显示真实已有任务的 `Overdue`、`Due today` 数量及最多 3 条最近待办。
- 从 workspace 根级和所有 gardens 的任务集合汇总，各记录只计数一次。
- 使用现有 `todayDate`、`careTaskStatus`；不使用 UTC 日期替代本地今天。
- 点击摘要进入 `/care?view=tasks`，列表标明 `All gardens` 或具体花园／种植区。
- 无任务时写 `No tasks due today`，提供 `Add task`，不占一张巨大的空白卡片。

### 2.4 花园分组

- 分组标题 `Your gardens`，右侧 `Add garden`。
- 桌面 3 列、平板 2 列、手机 1 列；以实际可用宽度判断，不按设备 User-Agent。
- 卡片包含缩略图、完整花园名称、种植区数量、`Open garden` 的明确语义。
- 卡片单击直接打开；不要求先选中再双击。
- 花园名允许两行正常换行；无空格长字符串也不能撑破卡片。
- 缩略图不重复渲染可交互按钮，整张导航卡片不嵌套按钮。
- 已有个人花园时，Demo Garden 放在分组末尾的次级入口。

### 2.5 次要工具

Plant Guide、Plant Doctor、跨花园 Next Season 总览可在页面末尾用紧凑链接行列出。它们不用五种背景色，也不与首屏 AI 输入区形成同等大小的卡片阵列。

8. 删除重复 eyebrow。页面标题前的眉题仅在提供额外层级信息时保留。
9. 植物颜色是业务标识，保留已有持久配色和自动区分算法；状态标识同时使用文字。
10. 减少动画：只用 120—160ms 的颜色／透明度变化；尊重 `prefers-reduced-motion`。

## 5. T01：修复草稿重置和编辑数据丢失

**目标：** 同一页面的其他操作、切换路由和返回都不会静默丢掉已输入内容。

**当前文件：** `src/components/GardenWorkspace.tsx` 的 `PlantingAreaInspector`、`updateAreaLayout`、`updateAreaPlacement`；`GrowingAreaLayoutEditor.tsx`；相关测试。

**具体实现：**

1. 种植区属性草稿以 `area.id` 标识，保存加载时的属性基线。dirty 比较 name、kind、length、width、rotation 的规范化值。
2. 替换依赖整个 `area` 的无条件重置。植物数量、植物位置和花园中的其他种植区变化不会触碰属性草稿。
3. 草稿干净时，同步真实属性变化；草稿脏时，如果相同属性被其他操作修改，保留草稿并显示对比／重新载入入口，避免悄悄覆盖。
4. 点击 Save 使用最新 workspace 的植物集合合并属性，不能用打开表单时捕获的旧 allocations 覆盖新植物。
5. 只有提交校验通过后才清除 dirty。字段错误时保留输入。
6. 改变种植区尺寸时，继续执行既有坐标约束。尚未提交的植物位置草稿若超出新边界，显示校验提示，不静默截断用户正在输入的文本。
7. 数字字段的编辑值用字符串保存，允许临时为空、输入小数；失焦或提交时校验、归一。不要每次按键就把空字符串强制转为 0。
8. 关闭检查面板有脏草稿时，显示 `Keep editing`／`Discard changes`。打开另一个种植区或模块时可以保留原草稿，返回时显示 `Unsaved changes`。

**跨路由草稿规则：** T02 的共享 provider 存放少量带实体键的草稿，不把整个表单数据写入每个 URL。不新增浏览器持久草稿存储，本轮保证同一标签页应用内导航保留；刷新／关闭页面有未保存草稿或未同步写入时，注册原生 `beforeunload` 提醒。浏览器可能不显示提醒，不能承诺刷新后恢复所有草稿。

实体被删除时，失效草稿不再允许保存；显示目标不存在并提供复制原文／丢弃草稿。保存或明确丢弃后清理对应草稿，避免无限累积。

**测试和验收：**

- 改种植区名称未保存，添加一株植物，名称输入仍在，植物也保留。
- 改名称未保存，移动植物／移动同一个种植区，名称输入仍在。
- 保存名称时不丢失刚添加的植物。
- 切到其他种植区再回来，未保存草稿仍在且有标识。
- 相同属性外部改变时有提示，草稿没有被替换。
- 空输入、`0`、负数、小数、无空格长名称具有可理解的反馈。
- dirty 时取消关闭保留草稿；确认放弃后恢复已保存值。

**排除：** IndexedDB、离线跨设备草稿、协作字段级合并、通用表单状态框架。

## 7. T03：两层反馈、连接恢复与可靠重试

**文件：** `src/hooks/useWorkspaceSync.ts`、`src/lib/gardenWorkspaceApi.ts`、AppShell、新 `SyncStatus`／`FormField`／`InlineNotice`；所有表单。

### 7.1 第一层：表单局部反馈

- 字段下方显示具体错误，设置 `aria-invalid`、`aria-describedby`。
- 提交多个错误时聚焦第一个错误字段；长表单顶部可显示短摘要和字段链接。
- 服务端业务错误放在本表单顶部，保持已填内容。
- 文案描述修正动作，例如 `Enter a length greater than zero.`，不暴露内部函数或数据库名。
- 本地修改完成可显示 `Record added`；在远端未确认前不显示 `All changes saved`。
- 生成 AI 草稿和保存 care 记录是两件事，各自有进行中／失败状态。

### 7.2 第二层：全局同步状态

把通用 `message: string` 中的同步含义提升为类型化状态；业务通知与同步状态分别存放。

| 状态 | 显示 | 操作 |
| --- | --- | --- |
| 初次恢复 | `Loading your workspace…` | 慢加载说明、超时后重试 |
| 浏览器本地模式 | `Saved on this device` | 连接不可用时说明尚未同步 |
| 等待／正在写入 | `Saving…` | 全站可见，保留输入能力 |
| 最新快照已确认 | `All changes saved` | 只在最新 workspace 与确认快照相同时出现 |
| 网络／普通错误 | `Changes not synced` | `Retry`，保留页面数据 |
| 存储写入失败 | `Changes could not be saved on this device` | 持续警告，不显示已保存 |
| revision 冲突 | `A newer version is available` | 查看／重新载入、明确覆盖选择 |

`isSynced` 的真实快照比较继续保留。存在未提交表单时，表单另有 `Unsaved changes`；全局已同步只描述已提交到 workspace 的快照，文案不能把未提交表单也宣称已保存。

### 7.3 重试与排队规则

1. `Retry` 显式把当前最新快照重新提交，不依赖“再修改一个字段”触发，也不能被相同 JSON 的去重判断拦住。
2. 同一 workspace 的写入继续串行，revision 在成功响应后更新。重试按钮在请求中禁用并防快速双击。
3. 重试发送最新 workspace，不重新执行新增记录动作，不重新生成记录 ID。
4. 保存失败后若又有新修改，最新快照中包含旧修改；最终成功才清除错误，不能旧请求成功就把新失败遮住。
5. 保存响应丢失时，服务端可能已经写入。后续 409 进入现有冲突流程，不自动覆盖。
6. 保留 import 在途期间的新编辑保护；冲突使旧队列失效的 generation 规则继续有效。
7. 自动网络重连可刷新连接提示；自动重新提交有写入意图的请求保持谨慎，本轮提供显式 Retry 即可。不增加无限重试循环。
8. 普通工作区 GET/PUT 推荐客户端 30 秒超时、5 秒后显示慢加载说明；超时视作状态不确定，保留本地数据。AI 请求单独管理，不能重用写入重试自动花费模型额度。
9. 本地模式 import 失败时允许继续本地使用；显示正确状态，不要求用户启动数据库。
10. SSR 和 `loading.tsx` 不替代浏览器恢复态，两者分别处理。

### 7.4 冲突提示

沿用“保留当前修改／重新载入服务器版本”，但明确后果：重新载入会放弃当前未同步 workspace 修改；保留当前修改会覆盖远端较新的 workspace。两个操作均需具体确认文案，保留已有安全测试。表单草稿是否仍有效按实体和属性基线重新核对。

**验收场景：** Next Season 添加记录时断网，页面可见未同步与 Retry；网络恢复后不再改字段也可保存；连点 Retry 不重复记录；再刷新能恢复已确认记录；409 不被当成一般错误重试；所有一级模块都显示一致状态。

| --- | --- | --- |

### 9.3 画布计算

- 读取容器可用宽度，使用 ResizeObserver；宽度为 0 的初始阶段显示占位，不参与坐标除法。
- Stage 的逻辑宽高与可用区域一致，避免仅用 CSS 拉伸固定 canvas，导致指针坐标偏移。
- 高度基准：桌面约 480px、平板约 420px、手机约 320px，按实际视口约束。它们是显示窗口，不改变米制 garden 数据。
- 根据当前 view bounds、padding、可用宽高计算统一 scale；渲染和拖动反算共享相同变换。
- `Focus beds` 与 `Full garden` 切换只改变视口，所有对象的米制坐标、尺寸、旋转保持不变。
- 正在拖动时固定本次拖动的坐标变换，结束后再重算 Focus bounds，避免对象跳动。
- 保留 0.1m 吸附、现有边界／旋转语义。发现几何模型其他缺陷单独列出，不混入重写。
- 旋转的种植区、负方向显示边界、很大花园＋很小种植区、空花园均测试。
- 小屏可通过文字列表选中并编辑；触控拖动不得抢走整个页面滚动。优先提供明确的 `Move` 模式或表单定位，普通浏览允许纵向滚动。

### 9.4 标签与非拖动操作

- 植物过小时隐藏圆内完整文本，选中后显示可读标签，详细列表始终保留名称。
- 实际展示的名称字号不低于 12px；圆形大小继续反映间距，不用扩大植物半径来放文字。
- 植物编辑保留 X/Y 位置；种植区面板新增对应米制位置输入，使移动操作不依赖拖动。
- 坐标输入与拖动使用同一个校验／吸附函数，确认输入后更新画布。
- 删除植物通过有文字的面板动作完成；移除仅 20px 的悬浮删除热点，避免误触和无键盘替代。
- Canvas 不承担唯一的信息访问方式。React-Konva 节点上的 aria-label 不等同于真正可聚焦的 DOM 控件。

**验收：** 390px 页面没有整体横向滚动；选中区域立即有可见编辑界面；关闭回到同一区域；1280px 窗口的编辑不要求滚过整张画布去找面板；1440px 适当内容宽度可同看画布和检查面板；拖动／表单定位与刷新后的米制坐标一致。

## 10. T06：统一删除、弹窗和键盘操作

**目标：** 删除后果明确，键盘和触控都可完成核心流程。

### 10.1 本轮删除策略

为控制实现风险，本轮对所有已持久化实体统一采用确认后删除。先不引入跨关联实体的撤销堆栈。

| 对象 | 交互 | 文案要素 |
| --- | --- | --- |
| 花园／种植区 | 危险确认弹窗 | 名称、实际受影响记录数量、哪些历史会保留 |

| 尚未保存的 AI 草稿行 | 可直接移除 | 原始笔记保留，可重新手动添加 |
| 尚未提交的表单 | 有修改时确认放弃 | Keep editing／Discard changes |

“归档”与“删除”按实际业务区别命名。不能宣称删除布局中的植物会删除所有历史，也不能写“仅此浏览器”而实际上同时写到服务器。

### 10.2 ConfirmDialog

- 优先使用原生 `<dialog>` 的 `showModal()`，保持唯一的共享确认入口。
- 有标题、描述与明确按钮：`Delete planting area`，避免只写 `Confirm`。
- `aria-labelledby` 关联标题，必要时 `aria-describedby` 关联简短描述。
- 默认焦点放取消；Tab 不穿透到背景；Escape 等同取消。
- 关闭后焦点回触发按钮；触发实体已删除时移到相邻列表项或列表标题。
- 长内容允许弹窗内滚动；操作区在小屏可见；背景不能滚动或被操作。
- 危险确认不依赖点击背景关闭；明确使用取消和 Escape。
- 提交时阻止重复确认。异步失败时保留弹窗上下文或在原位置提供可见失败反馈。
- 双面板／弹窗不互相嵌套出多个活跃焦点陷阱。

### 10.3 其他交互

- Care 的 Tasks／History 若采用 URL 导航，使用链接和 `aria-current`，不用 `role=tab`。
- 保留原地 tabs 时，补齐 roving tabindex、左右键、Home/End、aria-controls、tabpanel 关联，选择一种模型全站统一。
- 新建／编辑表单可见时焦点落到标题或首个合理字段，手机首页不自动聚焦 textarea 弹出键盘。
- 所有操作有文字或可访问名称；状态不只靠颜色。

**测试：** 真实浏览器验证 Tab/Shift+Tab/Escape/焦点恢复；取消删除不调用数据更新；确认只执行一次；目标消失的情况可处理；最小点击区与长文案在手机核对。

## 11. T07：Care、Season 和其他 AI 页的一致性

### 11.1 全局 Care 与花园 Care

## 12. T08：跨花园多事件 AI Garden Note

### 12.1 为什么独立列出

现有 `CareNoteDraftResponse` 是单条，`AiGardenNote` 以单个 gardenId 初始化；ADR-0058 的 `multiple` 明确不生成草稿；ADR-0060 的公开演示只使用受限示例范围。用户提出的“今天操作了好几个花园”需要真实增加多事件审核流程。

本节给出完整建议设计，批准后作为独立 ADR 实施。前端视觉改版可先完成，但整项用户目标不能在 T08 未完成时标为全部完成。

### 12.2 推荐数据模型决定

**一次笔记产生多条草稿，每条保存成现有的单目标 CareEvent。** 保留“一条记录一个目标”，本轮不增加多目标关联表和数据库迁移。批次是审核期间的前端状态，不新增可永久编辑的跨花园日志实体。

例子：

| 原文 | 结果 |
| --- | --- |
| 今天给前院番茄浇了水，给后院高床施了海藻肥 | 两条：前院／番茄／浇水；后院／高床／施肥；原文没说用量就留空 |
| 今天给前院和后院都浇水了；另有社区花园 | 两条特定花园记录，不能扩大成 All gardens |
| 今天所有花园都浇水了 | 一条 workspace 级 All gardens 记录，前提是该运行模式允许 |
| 今天没给前院浇水，明天给后院施肥 | 不生成已完成事件；保留解释，不偷偷转为任务 |
| 今天浇水了 | 可以形成待补目标的草稿，不默认上次选中花园 |
| 给前院和后院一共用了 20g 肥 | 无法确定每处用量，保持每条 amount 为空，保留总量原文与审核提示，不能给每处都填 20g |

### 12.3 运行范围与 API

建议新增 `POST /workspaces/{workspace_id}/ai/care-note-drafts`，保留旧单花园 `/gardens/{garden_id}/ai/care-note-draft` 契约。

- 第一版新端点面向非公开演示环境；`PORTFOLIO_DEMO=true` 时明确拒绝新批量端点，前端显示对应限制。
- runtime config 增加明确的 batch capability；字段缺失时按不支持处理，不能用请求失败猜能力。
- 请求为 `{ note, today }`，沿用最多 500 code points；today 校验沿用既有本地日期边界。
- 花园、种植区、植物上下文由服务器从当前 workspace 读取，不接受客户端伪造目标目录。
- 推荐单次最多 6 条草稿。超出时明确要求拆分，不能悄悄截断末尾事件。
- 批量生成只起草，不写 care history。落库仍由用户确认后沿用 workspace 保存与 revision。
- 不把一段原文按逗号机械拆开，也不对每个花园盲目调用一次模型。采用一次有界结构化提取，再做确定性校验与目标解析。

建议响应结构（定义独立类型，不破坏旧 `AiCareNoteDraft`）：

```ts
type CareNoteBatchDraftResponse = {
  drafts: Array<{
    sourceText: string;
    gardenId: string | null;
    type: "watering" | "fertilizing" | null;
    date: string | null;
    targetScope: "all-gardens" | "garden" | "planting-area" | "plant-group" | null;
    growingAreaId: string | null;
    plantingRecordId: string | null;
    fertilizerProduct: string | null;
    fertilizerAmount: number | null;
    fertilizerUnit: string | null;
    reviewNotes: string[];
  }>;
  notices: Array<{
    sourceText: string;
    reason: "planned" | "negated" | "unrelated" | "ambiguous" | "unsupported";
    message: string;
  }>;
};
```

上面是 API 响应，不是直接信任模型提供的 ID。模型原始输出定义独立严格 schema：事件分类、原文证据、gardenName、targetName 及可空字段；服务器解析到受信 ID。模型 schema 的所有字段 required、可缺信息用 null、所有对象 additionalProperties=false。严格 schema 支持范围在实际 provider 上验证，应用层再次做长度与范围校验。

响应里的 draftId 由前端生成并贯穿审核会话，保存后的 eventId 预先稳定生成；不同标识有清楚职责。旧 API 和旧测试保持有效。

### 12.4 确定性校验与歧义

1. 仅已完成、支持的 watering／fertilizing 事件进入可保存草稿。混合原文逐项分类，其他片段进入 notices。
2. 园名唯一匹配后，才在该 garden 内解析 area／plant。多个花园都有 Tomato、Bed 1 时不跨园猜测。
3. 原文缺失园名且只有一个可能的实体匹配，是否预填需在 ADR 明确；推荐要求唯一可验证匹配并展示完整目标路径，否则留空。
4. workspace 全范围与某花园全范围继续按明确文字证据核对；不能把所选多个花园偷换为全部花园。
5. 日期证据按对应事件片段和明确共享时间短语绑定。前院昨天、后院今天不能被统一成同一天；归属不清就留空。
6. sourceText 必须能在用户原文中定位；它只提供审核依据，不能当作证明抽取必然正确的保证。
7. 未知花园、跨花园目标 ID、不存在植物、非法日期、非正施肥量均不作为可保存值。
8. 提示注入文字作为笔记内容处理，不能改变允许字段、权限、provider、目标目录或保存规则。
9. 请求仍有超时、输入／输出上限，最多一次 provider 调用，不自动无限重试。批量输出预算独立于旧 800-token 单事件上限，在新 ADR 记录；本轮不修改线上成本限额。

### 12.5 审核页面

- 顶部保留原文和 `Review N records across M gardens`，不要求先把整段笔记绑定一个 garden。
- 每条草稿显示：包含勾选、具体花园、动作、日期、目标、可选肥料详情、关联原文、待补提示。
- 所有类型／日期／目标仍需用户核对。缺失关键值的已勾选行阻止整批保存，并聚焦错误。
- 默认选中有效已完成草稿；有待补字段的行也清楚标记，不静默丢掉。用户可显式取消勾选，保存按钮显示确切条数。
- `Add record` 可以手动添加另一条，`Remove draft` 删除未保存草稿；这些动作都保留原文。
- 切换某行花园只清空该行失效的 area／plant，不重置其他行、日期和原文。
- 修改原文后标记现有草稿与原文不一致；重新生成需要明确点击，并确认是否替换已修改的草稿。旧请求返回不得覆盖新原文。
- 正在生成、失败、空结果、多事件部分不支持、超出上限均有独立说明；手动录入始终可用。
- 保存成功后留在笔记完成态，显示写入多少条以及 `View records`／`Record more`。不强制跳进任意一个花园的历史页面。

### 12.6 保存与防重复

1. 新增纯函数 `applyCareDraftBatch`，输入最新 workspace 和已审核行。一次校验全部勾选行，再产生一个新 workspace。
2. 验证每行 owner 和实体仍存在。任何一条无效时，本次不写入任何行，保留全部草稿并指出错误。
3. workspace 全局记录写根 careEvents；其他记录写对应 garden.careEvents；不依赖 selectedGardenId。
4. 确认操作对本批次只应用一次，稳定 event IDs 在重试时复用。不要在 React state updater 中生成随机 ID。
5. 网络失败后标记“已加入当前工作区，尚未同步”，Retry 仅重发快照，不再次 apply 批次。
6. 同步成功后清理对应已应用草稿。409 保持现有冲突处理，重新载入远端如果放弃了本批次，要明确显示未保存并允许检查后重新应用。
7. 复用现有服务器 workspace 写入事务，核对其整批原子性。不能在前端 for-loop 中分别发多个互相无事务保证的保存请求。
8. 未增加服务器批次日志，本轮防重复范围是当前审核会话及同步重试；不宣称实现跨设备永久去重。

## 15. 明确禁止的交付捷径

1. 把 AI Garden Note 降为某个花园下面的小功能，或要求用户先点花园才可开始写原文。
2. 把“某几个花园”自动扩展为 All gardens。
3. 用假多行结果冒充真正的跨花园抽取。
4. 未经审核自动把 AI 输出写入历史。
5. 关闭冲突检查、吞掉保存错误或一直显示 Saved。
6. 用重置整个 workspace 的方式恢复一个表单或撤销一条记录。
7. 为统一 CSS 在末尾再加一整层覆盖，留下两套实际生效的设计规则。
8. 为视觉重构添加大型组件库、升级 Next／React、改变数据库模型而不记录和讨论理由。
9. 删除原测试让新 UI 通过，或以 mock 画布测试代替真实浏览器检查。
10. 顺手修改用户现有未提交文件、部署、打开公共 AI 新能力、进行付费验证。

## 16. 执行 agent 的最终汇报模板

逐任务报告 T00—T08 的完成／未完成状态，并给出：

- 实际用户工作流和本轮变化。
- 修改文件与 ADR。
- 测试命令、结果及失败／阻塞原因。
- 实际验证的视口与截图。
- 原有数据、AI 限额和部署配置是否保持。
- 未完成能力，尤其跨花园自动抽取与公开演示支持是否真的完成。
- 未提交／未推送状态；后续需要用户决定的具体事项。

## 17. 规范参考

以下用于实现语义和验收，不要求复制其视觉设计：

- [Next.js 15：Layouts and Pages](https://nextjs.org/docs/15/app/getting-started/layouts-and-pages)：文件路由与共享 layout。
- [WAI-ARIA APG：Modal Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)：弹窗焦点和键盘行为。

- [WCAG 2.2：Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)：24px 最低目标规则及例外；本项目主要触控操作采用更宽裕的 44px 设计目标。
- [WCAG 2.2：Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)：文字对比度测量。

这些规范不会自动证明本项目合规，最终需要针对实际页面核对。
